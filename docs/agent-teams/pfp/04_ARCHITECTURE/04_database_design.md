# Database Design

> Package: Anvex Agent Teams (multi-agent module) · PFP 5.7.0 · 2026-11-05

## Purpose

Define persistence so runs survive process death without touching the Anvex database (ARC-AND-2, ADR-016, PRD-FR-22).

## Scope

agents.db (Room 2.6.1, KSP) and the CAS directory. The existing `anvex.db` (schema version 13) is not modified.

## Requirements

Tables (all primary keys are string IDs generated by an injected `IdPort`):
| Table | Purpose |
|---|---|
| team | team name, project reference (projectId string), concurrency cap, budget caps |
| agent_profile | name, role text, provider reference, model, temperature, permissions JSON, limits |
| run | state, started/finished, base snapshot id |
| task | title, acceptance text, state, priority, claimed files JSON, attempts |
| task_dependency | task → prerequisite task |
| task_assignment | task, agent, workspace id, mode (primary or competitor) |
| event | sequence number (auto), runId, type, payload JSON, timestamp; append-only |
| changeset_ref | task, agent, base snapshot, result snapshot, state |
| gate | task, gate kind, state, decided by, decided at |
| usage_record | agent, task, input/output tokens, cost (nullable) |
| audit | sequence, actor, action, decision, evidence references |
| snapshot / snapshot_ref | CAS manifests and reference counts |
Rules: `provider reference` is an Anvex provider ID, never a key (ARC-SEC-2). Payload JSON is scrubbed by a denylist (key, token, secret, authorization, password) before insert and the insert fails if a match remains (AC-018). Schema snapshots are exported per version and verified in CI like the host's.

## Decisions

- Event log is the source of truth for scheduler state; tables are projections that can be rebuilt by replay (AC-005).
- A migration chain starts at version 1 for agents.db.

## Rules

1. Every migration has an automated test with a populated database.
2. No foreign key to anvex.db tables.
3. Deleting a team deletes its workspaces and releases CAS references in one transaction.

## Examples

After a kill, startup replays events for runs in `Running`, marks them `Interrupted`, and offers resume or discard.

## Future Considerations

Retention policies (event compaction) can be added because projections are rebuildable.
